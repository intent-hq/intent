### 5.48 Multiplayer — principals, invites, membership

The multi-principal surface of a daemon: who a connection *is*, which workspaces it may see, how an owner invites a second person and how that person joins. Introduced within protocol 10.3 by the intentd multiplayer stack — principals and caller binding ([intent-hq/intentd#1868](https://github.com/intent-hq/intentd/pull/1868)), message attribution ([#1869](https://github.com/intent-hq/intentd/pull/1869)), membership and capability enforcement ([#1870](https://github.com/intent-hq/intentd/pull/1870), [#1877](https://github.com/intent-hq/intentd/pull/1877), [#1871](https://github.com/intent-hq/intentd/pull/1871)), invite links and the `/invite` join ([#1872](https://github.com/intent-hq/intentd/pull/1872)). The join was reworked within 10.4 from a host-run GitHub device flow (`invite.redeem`, removed by [#1969](https://github.com/intent-hq/intentd/pull/1969)) into the **identity proof** — `invite.challenge` / `invite.prove` with the guest-side `github.identityProof.*` (§5.27) ([#1965](https://github.com/intent-hq/intentd/pull/1965), [#1967](https://github.com/intent-hq/intentd/pull/1967)) — plus the returning guest's `invite.inspect` / `invite.accept` ([#1963](https://github.com/intent-hq/intentd/pull/1963)), the owner-self-join refusal ([#1986](https://github.com/intent-hq/intentd/pull/1986)), reusable unpinned links ([#1988](https://github.com/intent-hq/intentd/pull/1988)) and the direct member add `principal.list` / `workspace.members.add` ([#2023](https://github.com/intent-hq/intentd/pull/2023), [#2025](https://github.com/intent-hq/intentd/pull/2025)). Protocol **10.6** ([versioning](../versioning.md)) makes the identity **provider-neutral** — a GitLab account is an identity: the additive `Principal.identity` triple, the `pinProvider` / `pinHost` pin params, the `invite.prove` `provider` / `host` / `proofId` params and the `sourceControl.identityProof.*` generalization of the guest-side proof (§5.27). The connection principal read `principal.me` is also summarized in §5.46 (client boot); presence, the ephemeral roster layered on top of membership, is §5.47.

Every method below is workspace-scoped unless stated otherwise. Five are **fast paths**: `workspace.invite.create` needs the listener's own pairing snapshot to build the link (like `pairing.getInfo`), and `invite.inspect` / `invite.accept` / `invite.challenge` / `invite.prove` are the only methods served on the unauthenticated `/invite` endpoint; the rest dispatch through the router. (`invite.redeem`, the pre-#1965 two-phase device-flow join, keeps its §5 fast-path catalog entry only until the intentd pin advances past its removal.)

#### Identity model

- A **principal** is a person. The daemon's existing single user is the **primary** principal — minted by migration `0125` and made the **owner** of every workspace that already existed — and every other principal is someone who joined through an invite, identified by the stable forge account that its identity proof established at first join (§ "Joining by invite"); a returning guest is re-bound to the same principal by its credential, no forge call. `login` / `displayName` / `avatarUrl` are the cached forge profile.
- **Identity triple (10.6).** A principal's forge account is the provider-neutral triple `identity: { provider, host, externalUserId }` — `provider` is `"github"` | `"gitlab"`, `host` the bare instance host (`"github.com"`, `"gitlab.com"`, a self-managed GitLab `host[:port]`), `externalUserId` the forge's stable account id **as a string** (GitHub's numeric id stringified; provider-agnostic storage). **One principal per triple** (partial unique index; `NULL` while unlinked): a GitHub user and a GitLab user with the same numeric id or the same login are two principals. The triple is **additive** on every wire projection of a principal — `principal.me`, `principal.list` rows, `workspace.members.list` Member rows — and omitted while the principal has no linked identity. The pre-10.6 GitHub key is kept and stays populated: `githubUserId?` (the integer, on `principal.list` rows) is still served for a `github` identity, and the migration backfills every existing row as `{ provider: "github", host: "github.com", externalUserId: String(githubUserId) }` with zero principal loss. Pins (`WorkspaceInvite.pinIdentity?`) and the owner-self-join refusal compare triples, never logins.
- **Which forge is the primary's identity (10.6).** The primary principal links the forge selected by the `identity.provider` setting (`"github"` | `"gitlab"` | `null`, §5.12): set and connected ⇒ that forge; `null` with exactly one forge connected ⇒ that one; `null` with both ⇒ the current identity if any, else `github` (the client prompts the user to choose). The identity is read from GitHub `GET /user` or GitLab `GET /api/v4/user`. Changing the setting is an **explicit re-key** of the primary's triple and publishes `principal:identity-changed` (§6); the identity lock below still blocks *implicit* re-keys (a token swap to another account of the same provider without a setting change).
- **Caller binding happens at the upgrade gate**, once per connection, from the presented bearer token: the legacy file token (`server.auth.token`) binds the primary principal as **administrator**; a per-principal credential (`principal_credential` row, matched by hex SHA-256 of the token) binds that principal as a **non-administrator**. An unknown token is still `401`. The binding never changes for the connection's lifetime and is never taken from `client.hello` — `principal.me` reports it. Agents (MCP) and the daemon itself act as the primary principal.
- **Roles** are per workspace: `owner` or `collaborator` (wire and stored spelling, lowercase). **Exactly one owner per workspace** — a partial unique index since migration `0126` — and there is no ownership transfer; the administrator is unconstrained by roles. `workspace.create` is administrator-only, so the owner is always the primary principal in v1.
- **Membership fields on every `Workspace` row** (§5.1) served through the service layer — `workspace.get`, `workspace.list`, the `workspace.subscribe` snapshot and deltas: `ownerPrincipalId?` (absent only on a transfer-imported row whose owner has not been re-derived yet), `myRole?` (`"owner"` | `"collaborator"`, relative to the request's bound caller; absent when the caller is not a member or no principal is bound), `memberCount` (the owner counts) and `openInviteCount`. Computed in one query per call, never per row.
- **Membership narrowing.** For a non-administrator caller `workspace.list` returns only its member workspaces, and every workspace-scoped read or write on a workspace it is not a member of is `-32602 { code: "not-found" }` — indistinguishable from a workspace that does not exist, so a guest can neither enumerate nor probe the owner's other workspaces. Owner-only operations attempted by a collaborator **member** are `-32003 Forbidden` (§ "Errors").

#### Invite links — `workspace.invite.create`

- `expiresInSecs` defaults to **7 days** (`604800`) and must be in `[1, 2592000]` (30 days), else `-32602`. `pinLogin?` restricts redemption to one forge account: it is trimmed (blank ⇒ unpinned), resolved **at mint time** on the forge `pinProvider?` / `pinHost?` name — GitHub `GET /users/{login}`, GitLab `GET /api/v4/users?username=` — and stored as the identity triple (`pinIdentity`; `pinLogin` is kept as the canonical login for display; `pinGithubUserId` is still populated for a github pin) — a login that names no account is `-32602 { code: "invite-pin-unknown" }`. **`pinProvider` / `pinHost` (10.6)** default to the host's **own** identity provider and host (§ "Identity model"), so a pre-10.6 client that sends `pinLogin` alone keeps its behavior on a GitHub-identity host; a `pinProvider` outside the enum is `-32602`. Because the pin is a triple, a GitHub user cannot redeem an invite pinned to a same-named GitLab login — the join is `invite-pin-mismatch`.
- **Inviting requires a linked forge identity.** The primary's cached identity alone does not qualify: the identity forge's auth status (`github.authStatus`, or `sourceControl.authStatus { provider: "gitlab" }`) must report a configured, working credential on every mint (the profile is fetched inline when the row is still unlinked), else `-32603 { code: "github-identity-required" }` — the code is kept for compatibility (10.6) but is raised only when **no** forge identity is linked, with a provider-neutral message; a host with a GitLab connection and no GitHub credential mints normally. A joined collaborator's identity was proven by its own identity proof and is accepted as cached — but `workspace.invite.create` is owner-only, so in v1 only the primary mints.
- **Guest cap.** Every open invite reserves a guest seat: when the workspace's collaborators plus its open invites already reach `sharing.maxGuestsPerWorkspace`, `create` is `-32602 { code: "guest-limit" }` (so N open links can never be redeemed against one remaining seat); a join that finds the collaborators alone at the cap is `workspace-full` and leaves the invite open. `workspace.members.list` reports the spend as `guestCount` / `guestLimit`.
- **Reusable links** ([intent-hq/intentd#1988](https://github.com/intent-hq/intentd/pull/1988)). An **unpinned** invite is reusable: any number of distinct forge accounts may join through it until it expires or is revoked (each join is one more collaborator; a member re-joining is idempotent), and its `redeemedAt` / `redeemedByPrincipalId` only record the **last** redemption while `redemptionCount` counts the memberships it created — the row stays in `workspace.invite.list` with `reusable: true`, and its `url` lets the owner re-share the same link. A **pinned** invite is single-use and closes on its redemption (`invite-redeemed` thereafter).
- **The link envelope is resolved exactly once per `create`, before the invite is minted**, so a daemon nobody can dial never stores an invite that cannot be redeemed: no TCP listener is `-32603 { code: "listener-down" }` (the `pairing.getInfo` discriminator); a listener with no dialable route (loopback-only bind and no tunnel) is `-32603` with a message naming `server.bindAddress` / `server.tunnel.enabled`. The envelope is the `intent://pair` one (§5.12 `pairing.getInfo`: loopback-free `hosts`, `port`, certificate `fingerprint`, optional tunnel `tcAddress`) **minus the bearer token**.
- **Link format** — `intent://invite?v=1&host=<ip[,ip…]>&port=<p>&fp=<sha256>&inviteId=<id>&secret=<s>[&tc=<addr>]`, with the same query encoding as `build_pairing_uri`. It never carries the daemon token: the holder can only redeem the invite.
- **Identity lock.** The first invite of a workspace also pins the workspace's *legacy author* (content authored before anyone else could have joined is the owner's — § "Attribution"). Once other principals or open invites exist, the primary's forge identity is load-bearing: a profile refresh that names a **different** account (the owner reconnected the forge as someone else) leaves the cached identity untouched and fails with `-32603 { code: "primary-identity-locked" }`. While the daemon is still single-user the switch is applied as before. An explicit `identity.provider` change (10.6) is not an implicit switch: it re-keys the primary on purpose; invites already pinned to the old identity are unaffected, new ones default to the new one.

#### Joining by invite — the `/invite` endpoint

`/invite` is the daemon's **one unauthenticated WebSocket endpoint** (beside `/ws` and `/tunnel`): the invitee holds only the link, so the upgrade skips credential resolution — the `server.enabled` flag and origin allow-list still apply (§2.2). It serves exactly four methods — `invite.inspect`, `invite.accept`, `invite.challenge`, `invite.prove` — and nothing else: any other method (request), `workspace.invite.create` included, is answered `-32001` with the message `the /invite endpoint serves invite.inspect, invite.accept, invite.challenge and invite.prove only`; a notification is dropped without a response; and reverse RPCs, subscriptions and events never flow on it. The host never runs an OAuth flow on the guest's behalf and never holds a guest token: a **first-time** guest proves it owns a forge account by publishing a host-issued nonce under that account (§ "The identity proof"); a **returning** guest presents the per-principal credential an earlier join minted (`invite.accept`). Every call requires an **open invite** — the secret is hashed and compared against the row; a miss (unknown id or wrong secret) is `-32602 { code: "invite-not-found" }`, a closed invite `invite-expired` / `invite-revoked` / `invite-redeemed` (the last only for a pinned link), and an invite whose workspace is gone `invite-not-found` — after the transport has validated the required string params (a missing or blank one is `-32602`).

**Bounds**, because an anonymous peer must not exhaust the daemon or a forge: at most **32** concurrent `/invite` connections (excess upgrades are refused `503`; the permit is taken before the `101` and returned when the connection task ends, however it ends), **16 KiB** inbound frames, at most **4** requests in flight per connection (excess is `-32603 { code: "invite-flow-busy" }`), a listener-wide token bucket over starts — the requests that hash a secret (**8** burst, one token per **5 s**; a throttled start is the same `invite-flow-busy`, answered before any store or upstream work, so a peer cannot enumerate links by serialising attempts or reconnecting), at most **8** outstanding nonces per invite and **256** daemon-wide (a `challenge` past either cap is `invite-flow-busy`). The same bounds apply whichever forge the proof names (10.6).

##### The identity proof — `invite.challenge` / `invite.prove`

1. **Challenge — `invite.challenge { inviteId, secret }`** → `{ workspaceId, workspaceTitle, hostname, prettyHostname, nonce, nonceExpiresAt }`. The host validates the open invite and issues a single-use **nonce** (32 random bytes, base64url unpadded, 10-minute lifetime) bound to the invite; `workspaceId` / `workspaceTitle` / `hostname` / `prettyHostname` let the guest's client name the workspace and host on its consent prompt (`invite.inspect` answers the same preview without spending a nonce). No forge is contacted.
2. **Publish** — the guest, on its **own** authenticated `/ws` connection to its own daemon, calls `sourceControl.identityProof.create { provider, host?, nonce, hostLabel }` (§5.27; `github.identityProof.create { nonce, hostLabel }` is the pre-10.6 alias) → `{ proofId, login, provider, host, externalUserId, avatarUrl, gistId? }` (`externalUserId` and `avatarUrl` always present, both `string | null`; `externalUserId` is the GitLab author id string and `null` for GitHub, whose identity the host resolves server-side from `gistId` / `login` in step 3 — clients must not depend on it for GitHub). Its daemon publishes the nonce with its stored forge token: on **GitHub** a **secret gist** with the single file `intent-join-proof.txt` whose first line is the nonce; on **GitLab** a **public personal snippet** (`POST /api/v4/snippets`, title naming Intent, one file whose first line is the nonce — public because the host verifies it anonymously; the guest's token needs the `api` scope). The guest's token never leaves the guest's daemon.
3. **Prove — `invite.prove { inviteId, secret, nonce, login, proofId, provider?, host? }`** (`gistId` is the pre-10.6 spelling of `proofId`; exactly one of the two). The host reads the proof back on the named forge — GitHub `GET /gists/{id}`; GitLab an **anonymous** read of the snippet metadata and raw content, falling back to an **authenticated** read with the host's **own** connection to the **same** `host` when the anonymous read is refused (`401` / `403` / a restricted `404`) — and requires: the owner (`author.username` on GitLab) equals `login` case-insensitively, the file's first line is the nonce, and the proof was created no earlier than the nonce was issued. Any mismatch, an unknown proof, or a nonce this host never issued for the invite (or already consumed) is `-32602 { code: "proof-invalid" }`; a nonce past its lifetime `proof-expired` (start over with `challenge`); the forge unreachable `-32603 { code: "github-unreachable" }` (the code is kept for both providers; the nonce stays valid for a retry); a GitLab host the daemon can neither read anonymously nor with a connection of its own is `-32603 { code: "identity-unverifiable", host }` with the message `cannot verify identity on <host>` (10.6; `error.data.host` names the instance). The nonce is consumed by the first attempt that reaches verification, except when the forge was unreachable. The identity then comes from the proof itself (GitHub: `GET /users/{login}`; GitLab: the snippet's `author` — `id`, `username`, `avatar_url` — no follow-up user call) and the join commits (below) → `{ status: "authorized", token, principalId, login, workspaceId }` — the **token exactly once**. The proven account being the **primary principal's own** is `-32602 { code: "owner-self-join" }`: the host owner cannot join its own host as a guest, no credential is minted and the invite stays open ([#1986](https://github.com/intent-hq/intentd/pull/1986); compared on the identity triple in 10.6).
4. **Clean up** — the guest deletes its proof: `sourceControl.identityProof.delete { provider, host?, proofId }` → `{ ok: true }` (idempotent; refuses to delete anything that is not a proof of this shape).
5. **Connect.** The guest reconnects on `/ws` (or through the tunnel route the link's `tc` names) with `token` as the bearer — the same hosts / port / fingerprint the link carried — and is bound as a non-administrator principal: `principal.me` names it (with its `identity`), `workspace.list` shows the joined workspace with `myRole: "collaborator"`, and every call is subject to the collaborator allowlist below.

**Returning guests — `invite.inspect` / `invite.accept`.** A guest that already holds a credential from this host (another workspace's join) skips the proof: `invite.inspect { inviteId, secret }` previews the invite, `invite.accept { inviteId, secret, credential }` resolves the principal from the credential's hash exactly like the `/ws` bearer gate (unknown or revoked ⇒ `-32602 { code: "credential-invalid" }` — join through the proof instead; bound to the primary ⇒ `owner-self-join`), checks a pin against the principal's **stored** identity and commits the join with that identity — no forge call, no profile refresh — answering the `prove` shape with a **fresh** credential (the presented one is rotated out). Works for a `gitlab` principal exactly as for a `github` one (10.6).

##### The join commit

The host re-checks the invite (still open; a pinned invite whose identity triple differs is `-32602 { code: "invite-pin-mismatch" }`) and, shared by `prove` and `accept`, in **one store transaction**: mints or reuses the principal keyed by the **identity triple** (10.6; `github_user_id` is dual-written for a `github` identity so pre-10.6 lookups keep resolving the same row) — a `prove` refreshes its cached `login` / `displayName` / `avatarUrl` — stamps the invite's redemption (the conditional update is the single-use guard of a **pinned** invite — a concurrent join that loses it is answered with the invite's closed state, `invite-redeemed`; a reusable invite stays open and only its last-redemption stamp moves), refuses when the workspace's collaborators already reach the guest cap `sharing.maxGuestsPerWorkspace` (`-32602 { code: "workspace-full" }`, invite left open) or the account is the primary principal's (`owner-self-join`, nothing minted), adds the `collaborator` membership (a returning principal re-joining a workspace it already belongs to keeps its row), and records a fresh per-principal credential (64 hex chars, stored as its SHA-256), consuming the `accept` credential when one was presented. After the commit `workspace:updated { changes: { members: true, invites: true, addedPrincipalId, memberCount } }` is published when a membership was added, `{ invites: true, memberCount }` alone for a member's re-join. `login` in the result is the joined principal's cached forge login.

**Credential revocation closes connections.** `principal.revokeSelf` (and any future revocation of a principal's credentials) broadcasts the principal id; every **non-administrator** connection still bound to it — the per-principal-credential ones; a connection admitted on the legacy token never subscribes to revocation, even when bound to the same primary principal — drains its in-flight responses (so the caller's own `revokeSelf` result is delivered, bounded to 5 s) and is then closed with WebSocket close code **1008 (policy)** and reason `credential revoked`. A replayed revoked token is refused at the upgrade gate (`401`). `workspace.members.remove` / `members.leave` do **not** close the connection: the removed member simply stops seeing the workspace — its later reads are `not-found`, its workspace-scoped subscription channels deliver nothing further, and its queued user messages on the workspace's agents are dropped.

#### Attribution — who wrote a human message

- **`fromPrincipalId` stamp.** Every user-origin entry point (`agent.sendMessage`, `agent.sendToTask`, `agent.queueMessage`, `agent.editQueuedMessage`, `agent.appendMessage`, `agent.editAndRegenerate`, `agent.wakeOrCreate`, `workspace.create`'s `initialAgent` message) stamps the bound wire caller's principal id into the message **metadata** under `fromPrincipalId` *before* the payload is persisted or enqueued — overwriting whatever the client supplied; an agent / daemon / unbound caller strips the key instead. Metadata only: the content is never annotated, so prompts stay byte-identical. A non-object `messageMetadata` is `-32602` (a human send must never fall back to the workspace default because its metadata had the wrong shape).
- **`author` projection.** Every `user` row served by `agent.getConversation` (slim and full), `agent.getSession`, `agent.getQueue`, the `chat.subscribe` snapshot / deltas and the `agent:message` / `agent:last-message` echoes carries `author: { principalId, login, displayName, avatarUrl }`, resolved at serve time from the row's `fromPrincipalId`, else the workspace's **legacy author** (the primary principal for workspaces that predate migration `0125`; pinned to the owner by the workspace's first invite otherwise), else its current owner. Profile fields are `null` when the principal row is gone; `author` is absent on non-user rows. Never persisted; a transcript page resolves its distinct authors in one batched statement.
- **Comment authors.** `comment.add` / `comment.respond` from a bound wire principal persist `author` = its login (else display name, else id) and `authorType: "user"` regardless of what the client supplied; the one pass-through is the primary principal with no GitHub identity linked (a single-user daemon keeps rendering the author its client always sent). Agents and the daemon keep their supplied values.

#### Events

Membership and invite changes ride `workspace:updated` (§6.5) with these `changes` keys, and every workspace-scoped read re-derives `memberCount` / `openInviteCount` / `myRole` from the store:

| Trigger | `changes` |
| --- | --- |
| join by invite (the `invite.prove` / `invite.accept` commit) | `{ members: true, invites: true, addedPrincipalId, memberCount }` |
| `workspace.members.remove` / `members.leave` / `principal.revokeSelf` (per workspace left) | `{ members: true, removedPrincipalId, memberCount }` |
| `workspace.invite.create` / `workspace.invite.revoke` (when a row changed) | `{ invites: true }` |

The removed member receives its own `removedPrincipalId` event as the last frame for that workspace (a `workspace.subscribe` delta maps it to `removedIds`); every other member sees the roster change and re-reads `workspace.members.list`.

**`principal:identity-changed` (10.6)** — the one daemon-global event of this surface: published when the primary principal's identity triple is re-keyed by an explicit `identity.provider` change (§ "Identity model"), payload `{ principalId, identity: { provider, host, externalUserId } | null }`. Clients holding a cached `principal.me` re-read it; member rows re-derive on their next read. Not published by the ordinary profile refresh (same account, updated `login` / `avatarUrl`).

#### Storage

Three intent-store migrations back this surface — `0125_principals.sql` (`principal`, `workspace_member` with the `owner` / `collaborator` role check, `principal_credential` keyed by token hash with `revoked_at`; `workspace.owner_principal_id` / `legacy_author_principal_id`; mints the primary principal and its owner rows), `0126_one_owner_per_workspace.sql` (partial unique index on `workspace_member (workspace_id) WHERE role = 'owner'`, repairing any duplicate owners first) and `0127_workspace_invites.sql` (`workspace_invite` with `secret_hash UNIQUE`, the pin columns and the redeemed / revoked stamps). The legacy file token is deliberately **not** copied into `principal_credential`: it stays the primary user's credential, honored beside the hashed rows. Workspace transfer nulls both principal columns and the target daemon re-derives the owner.

#### Capability probe

A successful, well-shaped `principal.me` reply proves the multiplayer surface; `isAdministrator` tells the client which side of the allowlist it is on. A refusal does not prove absence: a daemon without this surface answers `-32601` (the legacy token is the only credential it knows, so every connection is an administrator), while a multiplayer daemon answers a collaborator's unknown method with `-32003`.
