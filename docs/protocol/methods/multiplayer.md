### 5.47 Multiplayer — principals, invites, membership

The multi-principal surface of a daemon: who a connection *is*, which workspaces it may see, how an owner invites a second person and how that person joins. Introduced within protocol 10.3 by the intentd multiplayer stack — principals and caller binding ([intent-hq/intentd#1868](https://github.com/intent-hq/intentd/pull/1868)), message attribution ([#1869](https://github.com/intent-hq/intentd/pull/1869)), membership and capability enforcement ([#1870](https://github.com/intent-hq/intentd/pull/1870), [#1877](https://github.com/intent-hq/intentd/pull/1877), [#1871](https://github.com/intent-hq/intentd/pull/1871)), invite links and the gist identity-proof join ([#1872](https://github.com/intent-hq/intentd/pull/1872), [#1913](https://github.com/intent-hq/intentd/pull/1913), [#1963](https://github.com/intent-hq/intentd/pull/1963), [#1965](https://github.com/intent-hq/intentd/pull/1965), [#1967](https://github.com/intent-hq/intentd/pull/1967), [#1969](https://github.com/intent-hq/intentd/pull/1969)). Presence, the ephemeral roster layered on top of membership, is §5.46.

Every method below is workspace-scoped unless stated otherwise. Five are **fast paths**: `workspace.invite.create` needs the listener's own pairing snapshot to build the link (like `pairing.getInfo`), and the four guest join methods `invite.inspect` / `invite.accept` / `invite.challenge` / `invite.prove` are the only methods served on the unauthenticated `/invite` endpoint; the rest dispatch through the router. The guest's **own** daemon additionally serves the two administrator-only `github.identityProof.create` / `github.identityProof.delete` router methods that publish the proof gist (§5.27; listed there with the other `github.*` methods).

On the administrator a read also kicks a rate-limited background refresh of the primary's GitHub profile (never awaited; failures leave the cached row untouched) |
| principal.revokeSelf | — (daemon-global) | `{ revoked: true, credentials, workspaces }` — the bound **collaborator** leaves every workspace it collaborates in (`workspaces` = memberships dropped) and revokes all its credentials (`credentials` = rows revoked); the daemon then closes its connections (below). The administrator is `-32602` (rotate the server token or `github.revoke` instead) |
| workspace.members.list | workspaceId (req) | `{ members: Member[], guestCount, guestLimit }` — the roster, owner included, plus the guest cap's usage (`guestCount` = collaborators + open invites) and the effective `sharing.maxGuestsPerWorkspace` (§ "Guest caps"); Member+ (a non-member is `-32602 { code: "not-found" }`) |
| workspace.members.remove | workspaceId (req), principalId (req) | `{ removed: boolean }` — **owner-only**; removing the owner is `-32602`; a `principalId` that is not a member is `{ removed: false }` (no error). | workspace.invite.revoke | workspaceId (req), inviteId (req) | `{ revoked: boolean }` — **owner-only**; `revoked: false` when the invite was already closed; an `inviteId` unknown to this workspace is `-32602 { code: "not-found" }`. Publishes `workspace:updated { changes: { invites: true } }` when a row changed |

#### Identity model

- A **principal** is a person. The daemon's existing single user is the **primary** principal — minted by migration `0122` and made the **owner** of every workspace that already existed — and every other principal is someone who joined through an invite, identified by the stable GitHub account id (`github_user_id`, one principal per account) that its gist identity proof established (§ "Joining by invite"). `login` / `displayName` / `avatarUrl` are the cached GitHub profile.
- **Caller binding happens at the upgrade gate**, once per connection, from the presented bearer token: the legacy file token (`server.auth.token`) binds the primary principal as **administrator**; a per-principal credential (`principal_credential` row, matched by hex SHA-256 of the token) binds that principal as a **non-administrator**. An unknown token is still `401`. The binding never changes for the connection's lifetime and is never taken from `client.hello` — `principal.me` reports it. Agents (MCP) and the daemon itself act as the primary principal.
- **Roles** are per workspace: `owner` or `collaborator` (wire and stored spelling, lowercase). **Exactly one owner per workspace** — a partial unique index since migration `0123` — and there is no ownership transfer; the administrator is unconstrained by roles. `workspace.create` is administrator-only, so the owner is always the primary principal in v1.
- **Membership fields on every `Workspace` row** (§5.1) served through the service layer — `workspace.get`, `workspace.list`, the `workspace.subscribe` snapshot and deltas: `ownerPrincipalId?` (absent only on a transfer-imported row whose owner has not been re-derived yet), `myRole?` (`"owner"` | `"collaborator"`, relative to the request's bound caller; absent when the caller is not a member or no principal is bound), `memberCount` (the owner counts) and `openInviteCount`. Computed in one query per call, never per row.
- **Membership narrowing.** For a non-administrator caller `workspace.list` returns only its member workspaces, and every workspace-scoped read or write on a workspace it is not a member of is `-32602 { code: "not-found" }` — indistinguishable from a workspace that does not exist, so a guest can neither enumerate nor probe the owner's other workspaces. Owner-only operations attempted by a collaborator **member** are `-32003 Forbidden` (§ "Errors").

#### Invite links — `workspace.invite.create`

- `expiresInSecs` defaults to **7 days** (`604800`) and must be in `[1, 2592000]` (30 days), else `-32602`. `pinLogin?` restricts redemption to one GitHub account: it is trimmed (blank ⇒ unpinned), resolved through `GET /users/{login}` **at mint time** and stored as the stable account id (`pinGithubUserId`; `pinLogin` is kept as the canonical login for display) — a login that names no account is `-32602 { code: "invite-pin-unknown" }`.
- **Inviting requires a linked GitHub identity.** The primary's cached identity alone does not qualify: `github.authStatus` must report a configured, working credential on every mint (the profile is fetched inline when the row is still unlinked), else `-32603 { code: "github-identity-required" }`. A joined collaborator's identity was proven by its own gist proof and is accepted as cached — but `workspace.invite.create` is owner-only, so in v1 only the primary mints.
- **The link envelope is resolved exactly once per `create`, before the invite is minted**, so a daemon nobody can dial never stores an invite that cannot be redeemed: no TCP listener is `-32603 { code: "listener-down" }` (the `pairing.getInfo` discriminator); a listener with no dialable route (loopback-only bind and no tunnel) is `-32603` with a message naming `server.bindAddress` / `server.tunnel.enabled`. The envelope is the `intent://pair` one (§5.12 `pairing.getInfo`: loopback-free `hosts`, `port`, certificate `fingerprint`, optional tunnel `tcAddress`) **minus the bearer token**.
- **Link format** — `intent://invite?v=1&host=<ip[,ip…]>&port=<p>&fp=<sha256>&inviteId=<id>&secret=<s>[&tc=<addr>]`, with the same query encoding as `build_pairing_uri`. It never carries the daemon token: the holder can only redeem the invite.
- **Identity lock.** The first invite of a workspace also pins the workspace's *legacy author* (content authored before anyone else could have joined is the owner's — § "Attribution"). Once other principals or open invites exist, the primary's GitHub identity is load-bearing: a `GET /user` refresh that names a **different** account (the owner reconnected GitHub as someone else) leaves the cached identity untouched and fails with `-32603 { code: "primary-identity-locked" }`; a mint whose identity changed under it is `-32603` ("retry"). While the daemon is still single-user the switch is applied as before.

##### Re-copyable links — `url` on `workspace.invite.list`

The plaintext secret is stored beside its hash (migration `0125`) so the owner can copy an open invite's link again: every `list` row rebuilds `url` from the stored secret through the **current** link envelope (host / port / fingerprint / `tc` as the listener reports them at read time). It names the same invite and carries the same secret as the minted link, but the bytes are **not** guaranteed identical across calls — if the daemon's route changed since the mint, the re-copied link reflects the new route. `url` is **absent, never an error**, when the row predates the stored secret or when no link can be built at read time (listener down, no dialable route) — a `list` whose envelope fails to resolve still answers every open row, just without `url`. The envelope is resolved once per call, not per row. On `create`, the one link formatted from the single pre-mint envelope is stamped as both `invite.url` and the top-level `url`, so the two are the same string by construction.

#### Joining by invite — the `/invite` endpoint

`/invite` is the daemon's **one unauthenticated WebSocket endpoint** (beside `/ws` and `/tunnel`): the invitee holds only the link, so the upgrade skips credential resolution — the `server.enabled` flag and origin allow-list still apply (§2.2). It serves exactly four methods — `invite.inspect`, `invite.accept`, `invite.challenge`, `invite.prove` — and nothing else: any other method (request), `workspace.invite.create` included, is answered `-32001` with the message `the /invite endpoint serves invite.inspect, invite.accept, invite.challenge and invite.prove only`; a notification is dropped without a response; and reverse RPCs, subscriptions and events never flow on it. The host never authenticates a guest against GitHub itself and never sees the guest's GitHub token: a **first-time guest** proves its identity from its **own** daemon with a gist identity proof (`invite.challenge` → `invite.prove`), and a **returning guest** that already holds a credential this host minted joins with it (`invite.accept`, optionally preceded by the `invite.inspect` preview). Every `/invite` method requires an **open invite before any successful operation** — the secret is hashed and compared in constant time against the row; a miss (unknown id or wrong secret) is `-32602 { code: "invite-not-found" }`, a closed invite `invite-expired` / `invite-revoked` / `invite-redeemed`, and an invite whose workspace is gone `invite-not-found` — but the invite check is **not** always the first one, so a request that is wrong in several ways gets the earliest refusal in this order: (1) the transport validates the required string params (a missing or blank one is `-32602 { code: "invalid-params" }`); (2) `invite.accept` resolves the presented credential and its GitHub identity **before** opening the invite, so an unknown / revoked credential is `credential-invalid` even against a closed or nonexistent invite, and `invite.prove` checks the `login` / `gistId` syntax (`invalid-params`) before the invite; (3) the invite is opened; `invite.inspect` / `invite.challenge` go straight from (1) to (3).

**Bounds**, because an anonymous peer must not exhaust the daemon or GitHub: at most **32** concurrent `/invite` connections (excess upgrades are refused `503`; the permit is taken before the `101` and returned when the connection task ends, however it ends), **16 KiB** inbound frames, at most **4** requests in flight per connection (each runs on its own task, so heartbeats keep flowing while an `invite.prove` waits on GitHub; excess is `-32603 { code: "invite-flow-busy" }`), a listener-wide token bucket over every `/invite` request — all four hash a secret — (**8** burst, one token per **5 s**; a throttled request is the same `invite-flow-busy`, answered before any store or upstream work, so a peer cannot enumerate links or churn nonces by serialising attempts or reconnecting), and nonce caps — **8** outstanding nonces per invite and **256** daemon-wide (an `invite.challenge` past either cap is `invite-flow-busy`). The two caps differ in strength: the 256 is a **hard invariant** (every outstanding nonce holds one of 256 daemon-wide permits from issuance until it is spent or purged, including while an `invite.prove` is in flight on it); the per-invite 8 is an **admission check at issuance** against the invite's pending nonces — a nonce taken off the pending set by an in-flight `prove` and **put back** after a `github-unreachable` failure is re-added without re-checking the cap, so a concurrent `challenge` issued in between can leave the invite transiently at 9. Clients must not assume "at most 8" as a strict bound.

##### First-time guest — the gist identity proof

The guest client drives two daemons: the **host** (over `/invite`) and its **own** daemon (over its ordinary authenticated connection, where it is the administrator). The host learns *who* the guest is — the stable GitHub account id — and nothing else.

1. **Preview (optional) — `invite.inspect { inviteId, secret }`** on the host → `{ workspaceId, workspaceTitle, hostname, prettyHostname }` (`hostname` / `prettyHostname` are always present — the host's own, the same values `system.status` / `server.pairingInfo` report). Reads only and issues nothing, so it is a **preflight** a client may skip: the reference client ([intent-hq/cloudlands-fe#2586](https://github.com/intent-hq/cloudlands-fe/pull/2586)) starts a first-time join directly at `invite.challenge`, whose result carries the same four preview fields, and uses `inspect` only on the returning-guest path. A client that holds a credential for this host tries the returning-guest path (below) first and falls back to the proof on `credential-invalid`. **Rendering the preview** (client guidance, not a wire change): the host label is the first non-blank of `prettyHostname` → `hostname` → the address the client dialed, except that a `tc` (Tailscale-relay) address is opaque and renders as a localized "Unknown host" — and that label, not the address, is what the client passes as `hostLabel` in step 3, so an opaque relay address is never copied into the gist; a blank `workspaceTitle` renders as "Untitled". A client that must also talk to older hosts should treat the two host-name fields as optional on read.
2. **Challenge — `invite.challenge { inviteId, secret }`** on the host → the `inspect` result plus `nonce` and `nonceExpiresAt`. The nonce is **32 random bytes** as unpadded base64url (43 chars), **single-use**, bound to this `inviteId`, and lives **10 minutes** (`nonceExpiresAt`, RFC 3339 UTC). Issuing it takes a daemon-wide permit and counts against the invite's outstanding nonces (the caps above); expired nonces are purged when the next one is issued.
3. **Publish — `github.identityProof.create { nonce, hostLabel }`** on the guest's **own** daemon (§5.27; administrator-only) → `{ gistId, login }`. The guest daemon uses only its **stored** `github.connect` token (never the env / `gh` fallbacks), confirms via `GET /user` that the token's `X-OAuth-Scopes` grant `gist` (else `-32603 { code: "github-scope-missing" }` — a **scope** test, not a token-age test: any stored token whose `X-OAuth-Scopes` does not list `gist`, including one whose scopes GitHub reports as absent, is refused and must be reauthorized via `github.connect`, which requests `gist` by default since [intent-hq/intentd#1965](https://github.com/intent-hq/intentd/pull/1965) — a token connected before that is one common cause; no stored token is `github-not-connected`; a transport failure is `github-unreachable`; any other forge / decode failure is a plain `-32603` without a guaranteed `data.code`, §5.27), and `POST /gists` a **secret** gist whose single file `intent-join-proof.txt` has the nonce on its first line and a human note naming `hostLabel` on the second (`hostLabel` is free text for that note — e.g. the host's `prettyHostname` — trimmed, non-empty, no control characters, like `nonce`). `login` is the token owner's login as GitHub reports it. The guest's token never crosses the wire.
4. **Prove — `invite.prove { inviteId, secret, nonce, gistId, login }`** on the host. `login` must be a GitHub login (1–39 alphanumerics or hyphens) and `gistId` alphanumeric, else `-32602 { code: "invalid-params" }`. The host consumes the nonce under its lock — exactly one concurrent attempt gets the slot, every other one is `proof-invalid`; a nonce issued for another invite is `proof-invalid`, one past its lifetime `proof-expired` — then reads the gist back (`GET /gists/{gistId}`, with the **host's** resolved source-control credential — the ordinary stored `github.connect` token → `GITHUB_TOKEN` / `GH_TOKEN` env → `gh auth token` chain, §5.27 — and anonymously only when none of those resolves: a secret gist is unlisted, not private; note this is looser than the guest side, whose `identityProof.*` calls are stored-token-only) and accepts it only if **all** hold: the gist's owner login equals `login` (case-insensitively), `intent-join-proof.txt` exists and its trimmed first line equals the nonce, and the gist's `created_at` is not earlier than the nonce's issue time (second precision). It then resolves the account with `GET /users/{login}` (the authority on the stable id; its login must match the gist owner too). The two failure classes differ in what happens to the nonce: a gist (or account) that was **fetched and decoded but fails a comparison** — owner ≠ `login`, missing file, wrong first line, `created_at` before the nonce — or a **404** on either read (unknown gist, unknown login) is `-32602 { code: "proof-invalid" }` with the nonce **spent**; a gist or account the host **could not fetch or decode** — GitHub unreachable, a non-404 HTTP error (server error, auth or rate-limit refusal), or a response the host cannot decode, including one missing `owner.login` or `created_at` — is `-32603 { code: "github-unreachable" }` with the nonce **put back** for a retry within its lifetime. **Client recipe** for a refusal: after `github-unreachable` the nonce is still live, so a client *may* retry `prove` with the same nonce within its lifetime (the reference client currently surfaces it as a failure instead); on `proof-invalid` / `proof-expired` the reference client deletes the gist (step 5), asks the user, and — **once in total across both codes** — requests a fresh challenge (step 2) and publishes a fresh proof; a second refusal surfaces as the failure. On success the join commits (below) and the result is `{ status: "authorized", token, principalId, login, workspaceId }` — the **token exactly once**.
5. **Clean up — `github.identityProof.delete { gistId }`** on the guest's own daemon → `{ ok: true }` (idempotent; an already-deleted gist is `ok`). Same stored-token-only rule as `create` but its own failure set — `github-not-connected`, `github-unreachable`, otherwise a plain `-32603`; it performs no scope check and never emits `github-scope-missing` (§5.27). Best-effort: the proof gist is safe to leave behind.
6. **Connect.** The invitee reconnects on `/ws` (or through the tunnel route the link's `tc` names) with `token` as the bearer — the same hosts / port / fingerprint the link carried — and is bound as a non-administrator principal: `principal.me` names it, `workspace.list` shows the joined workspace with `myRole: "collaborator"`, and every call is subject to the collaborator allowlist below.

##### Returning guest — `invite.inspect` → `invite.accept`

A guest that already holds an active per-principal credential for this host (from an earlier join to any of its workspaces) skips the proof on later invites: after the `inspect` preview (the reference client shows the consent prompt from it; the daemon does not require the call) it calls **`invite.accept { inviteId, secret, credential }`** with that credential as its proof of identity. The host resolves it exactly as the `/ws` bearer gate would (active credentials only; a revoked one is refused here as it would be at upgrade) to a principal that carries a GitHub identity — the one its earlier gist proof established — enforces the pin against that account, and commits the join with the stored identity; GitHub is never contacted. The presented credential is **consumed inside the join transaction** ([intent-hq/intentd#1967](https://github.com/intent-hq/intentd/pull/1967)): at commit time it must match **exactly one active credential row owned by the joining principal**, and that row is replaced atomically by the fresh credential the result carries — or the whole join is refused `-32602 { code: "credential-invalid" }` with nothing written. Only the **presented** credential is rotated: any *other* active credentials the principal holds for this host (e.g. from earlier independent proof joins) are unaffected, so a guest may legitimately hold several; connections still bound to the old one keep working until they close; and of two concurrent accepts presenting the **same** credential exactly one mints — the loser is refused with nothing written, as `credential-invalid` when the credential row is the check that fails, though when both target the **same invite** the winner's commit also redeems it, so the loser's transaction already fails its open-invite check and answers `invite-redeemed` instead. A credential unknown to this host, revoked, or bound to a principal without a GitHub identity is `credential-invalid` — the client falls back to the gist proof.

##### The join commit (shared by `invite.prove` and `invite.accept`)

The join re-checks the invite (still open; a pinned invite whose account differs is `-32602 { code: "invite-pin-mismatch" }`) and, in **one store transaction** (`BEGIN IMMEDIATE`), checks the guest cap (a workspace whose collaborators already reach `sharing.maxGuestsPerWorkspace` is `-32602 { code: "workspace-full" }` — nothing is written and the **invite stays open**; § "Guest caps"), mints or reuses the principal keyed by `github_user_id`, marks the invite redeemed (the conditional update is the single-use guard — a concurrent join that loses it is answered with the invite's closed state, `invite-redeemed`), adds the `collaborator` membership, records a fresh per-principal credential (64 hex chars, stored as its SHA-256) and, for `invite.accept`, revokes the presented one. `workspace:updated { changes: { members: true, invites: true, addedPrincipalId, memberCount } }` is published after the commit. The result `{ status: "authorized", token, principalId, login, workspaceId }` carries the **token exactly once**; `login` is the joined principal's cached GitHub login.

#### Guest caps — `[sharing]` settings ([intent-hq/intentd#1917](https://github.com/intent-hq/intentd/pull/1917))

Three daemon-owned `sharing.*` settings (§5.12; TOML-backed under a `[sharing]` config.toml section) bound how many guests a workspace admits and how many WSS connections guests may hold. The exemption is by **credential class**, not by account: the administrator (legacy) token and the UDS path are never counted; every **per-principal credential** is counted — including one bound to the primary GitHub account, if such a credential exists. The membership cap counts collaborator memberships and open invites (below), which the owner never holds.

- `sharing.maxGuestsPerWorkspace` — number, default `10`, `0..=100` (`0` closes every workspace to guests). **Live**: read on every mint and join.
- `sharing.maxGuestConnections` — number, default `40`; `0` = unlimited, else `1..=100000`. **Live** ([intent-hq/intentd#1918](https://github.com/intent-hq/intentd/pull/1918)): the admission gate reads the current value on every guest upgrade, so a `settings.update` or a config.toml live-reload applies to the **next** admission without a listener or daemon restart. It never evicts: lowering the cap below the number of seats currently held disconnects nobody — new guest upgrades are refused until connections drain below the new cap. One live cell is shared by every listener the daemon builds, so a runtime listener toggle keeps the current values rather than resurrecting boot-time ones.
- `sharing.maxConnectionsPerGuest` — number, default `4`; `0` = unlimited, else `1..=1000`. Same live rule as above: held seats are compared against the new per-guest cap on the principal's next upgrade; nothing held is revoked.

- **Membership cap (`maxGuestsPerWorkspace`).** Every open invite reserves a guest seat, so the cap is spent by **collaborators plus open invites** (`workspace.members.list`'s `guestCount`, against `guestLimit`): `workspace.invite.create` is refused with `-32602 { code: "guest-limit" }` when `guestCount >= guestLimit` — checked after the caller's identity is qualified (the inviting principal's GitHub identity is verified, and refreshed if needed, first) but before the pin lookup, and again under the mint lock right before the insert, so two concurrent mints cannot both take the last seat. The **join** (the commit shared by `invite.prove` and `invite.accept`) compares **collaborators alone** against the cap inside the join transaction (`BEGIN IMMEDIATE`, so two concurrent joins cannot overshoot): over the cap it is `-32602 { code: "workspace-full" }`, writes nothing and leaves the invite open for a later attempt; a returning collaborator re-joining takes no new seat and is never refused this way. Neither refusal publishes an event. The owner makes room by `workspace.invite.revoke` / `workspace.members.remove` (or raising the setting).
- **Connection caps (`maxGuestConnections` / `maxConnectionsPerGuest`).** At the `/ws` upgrade gate, after the bearer token resolves to a per-principal credential and before the `101`, the connection takes one listener-wide seat and one seat of its own principal; when either cap is spent the upgrade is refused with **HTTP `503 Service Unavailable`** carrying **`Retry-After: 30`** (delta-seconds; the constant `GUEST_CAP_RETRY_AFTER_SECS`, [intent-hq/intentd#1918](https://github.com/intent-hq/intentd/pull/1918)) and the socket is destroyed (otherwise the same bodyless shape as the `401` / `403` refusals, §2.1). The header is specific to the guest-cap refusal — no other upgrade refusal (`401`, `403`, `404`, the `/invite` 32-connection `503`) carries it. A seat frees on a disconnect or a raised cap, neither of which the daemon can predict, so the hint is a fixed back-off rather than an estimate: clients **should** honour the delta-seconds value before retrying the upgrade (and **must not** tight-loop on `503`); a client that meets a guest-cap `503` without the header (a pre-#1918 daemon) should fall back to the same 30 s. Both seats are checked and taken under one lock and are returned when the connection task ends — clean close, remote close, panic, or the heartbeat reaper aborting it — so a reaped connection frees its seats like a clean exit. `/tunnel` is owner-only (a per-principal credential is refused there with `403` before the caps are consulted), and `/invite` carries no credential, so neither is counted.
- **`GET /health`** (§1.1) carries the additive `guestConnections` — guest connections currently admitted — beside `clients`: `{ "status": "ok", "clients": <n>, "guestConnections": <n> }`.

**Credential revocation closes connections.** `principal.revokeSelf` (and any future revocation of a principal's credentials) broadcasts the principal id; every **non-administrator** connection still bound to it — the per-principal-credential ones; a connection admitted on the legacy token never subscribes to revocation, even when bound to the same primary principal — drains its in-flight responses (so the caller's own `revokeSelf` result is delivered, bounded to 5 s) and is then closed with WebSocket close code **1008 (policy)** and reason `credential revoked`. A replayed revoked token is refused at the upgrade gate (`401`). `workspace.members.remove` / `members.leave` do **not** close the connection: the removed member simply stops seeing the workspace — its later reads are `not-found`, its workspace-scoped subscription channels deliver nothing further, and its queued user messages on the workspace's agents are dropped.

#### Attribution — who wrote a human message

- **`fromPrincipalId` stamp.** Every user-origin entry point (`agent.sendMessage`, `agent.sendToTask`, `agent.queueMessage`, `agent.editQueuedMessage`, `agent.appendMessage`, `agent.editAndRegenerate`, `agent.wakeOrCreate`, `workspace.create`'s `initialAgent` message) stamps the bound wire caller's principal id into the message **metadata** under `fromPrincipalId` *before* the payload is persisted or enqueued — overwriting whatever the client supplied; an agent / daemon / unbound caller strips the key instead. Metadata only: the content is never annotated, so prompts stay byte-identical. A non-object `messageMetadata` is `-32602` (a human send must never fall back to the workspace default because its metadata had the wrong shape).
- **`author` projection.** Every `user` row served by `agent.getConversation` (slim and full), `agent.getSession`, `agent.getQueue`, the `chat.subscribe` snapshot / deltas and the `agent:message` / `agent:last-message` echoes carries `author: { principalId, login, displayName, avatarUrl }`, resolved at serve time from the row's `fromPrincipalId`, else the workspace's **legacy author** (the primary principal for workspaces that predate migration `0122`; pinned to the owner by the workspace's first invite otherwise), else its current owner. Profile fields are `null` when the principal row is gone; `author` is absent on non-user rows. Never persisted; a transcript page resolves its distinct authors in one batched statement.
- **Comment authors.** `comment.add` / `comment.respond` from a bound wire principal persist `author` = its login (else display name, else id) and `authorType: "user"` regardless of what the client supplied; the one pass-through is the primary principal with no GitHub identity linked (a single-user daemon keeps rendering the author its client always sent). Agents and the daemon keep their supplied values.

#### Events

No new event type: membership and invite changes ride `workspace:updated` (§6.5) with these `changes` keys, and every workspace-scoped read re-derives `memberCount` / `openInviteCount` / `myRole` from the store:

| Trigger | `changes` |
| --- | --- |
| join by invite (redeem commit) | `{ members: true, invites: true, addedPrincipalId, memberCount }` |
| `workspace.members.remove` / `members.leave` / `principal.revokeSelf` (per workspace left) | `{ members: true, removedPrincipalId, memberCount }` |
| `workspace.invite.create` / `workspace.invite.revoke` (when a row changed) | `{ invites: true }` |

The removed member receives its own `removedPrincipalId` event as the last frame for that workspace (a `workspace.subscribe` delta maps it to `removedIds`); every other member sees the roster change and re-reads `workspace.members.list`.

#### Storage

Four intent-store migrations back this surface — `0122_principals.sql` (`principal`, `workspace_member` with the `owner` / `collaborator` role check, `principal_credential` keyed by token hash with `revoked_at`; `workspace.owner_principal_id` / `legacy_author_principal_id`; mints the primary principal and its owner rows), `0123_one_owner_per_workspace.sql` (partial unique index on `workspace_member (workspace_id) WHERE role = 'owner'`, repairing any duplicate owners first), `0124_workspace_invites.sql` (`workspace_invite` with `secret_hash UNIQUE`, the pin columns and the redeemed / revoked stamps) and `0125_workspace_invite_secret.sql` (nullable plaintext `secret` for re-copyable links). The legacy file token is deliberately **not** copied into `principal_credential`: it stays the primary user's credential, honored beside the hashed rows. Workspace transfer nulls both principal columns and the target daemon re-derives the owner.

#### Capability probe

A successful, well-shaped `principal.me` reply proves the multiplayer surface; `isAdministrator` tells the client which side of the allowlist it is on. A refusal does not prove absence: a daemon without this surface answers `-32601` (the legacy token is the only credential it knows, so every connection is an administrator), while a multiplayer daemon answers a collaborator's unknown method with `-32003`.
